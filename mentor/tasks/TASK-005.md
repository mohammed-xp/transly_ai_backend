# 🎫 TASK-005 — الـ AI proxy يفشل بصدق

**Milestone:** AI proxy (بين M2 و M4) · **الوقت المتوقع:** ~120 دقيقة · **الصعوبة:** ▓▓▓▓░
**اتفتحت:** 2026-08-19

---

## الهدف

دلوقتي `TranslateAsync` بيرجّع `null` في **كل** حالة فشل، والـ controller بيحوّلها لـ **502 واحدة** مهما كان اللي حصل. يعني:

- الـ quota خلصت (زي اللي حصل حرفياً أثناء review TASK-004) → التطبيق بيشوف "Bad Gateway"
- الـ API key غلط → التطبيق بيشوف "Bad Gateway"
- Gemini رفض النص لأسباب safety → التطبيق بيشوف "Bad Gateway"
- Gemini نفسه واقع → التطبيق بيشوف "Bad Gateway"

واحدة بس من الأربعة دول صح.

بعد التاسك دي: كل حالة ليها status code مختلف وسبب معلن، والتطبيق يقدر يقرر يعمل ايه (يعيد المحاولة؟ يقول للمستخدم النص مرفوض؟ يسكت؟) من غير ما يخمّن.

## ليه دلوقتي

القرار **#16** في `progress.md` قال بالنص: الـ `null` كفاية دلوقتي، و**يتحوّل أول ما نحتاج نفرّق 429 عن 502 عن 500**. اللحظة دي جت — وانت شفتها بعينك في review TASK-004 لما الـ free tier خلص والـ log قال `GenerateRequestsPerDayPerProjectPerModel-FreeTier`.

كمان ده الأساس اللي M4 (error contract) هيتبني عليه. لو الـ service مش عارف يفرّق بين أنواع الفشل، مفيش `IExceptionHandler` مركزي هيعرف يفرّق نيابةً عنه.

### الجزء أ — تقليل عدد الحالات قبل ما تصنّفها

> **معدّلة 2026-08-20 بعد اعتراض منه.** كان اسمها "تسخين" وكانت فيها 3 بنود. التسمية دي غلط مني — خلّت البنود تبان زي التنضيف. البندين اللي فضلوا **مدخلات للجزء ب مش حاجة جنبه**: كل واحد فيهم بيتصرف في حالة فشل قبل ما توصل للتصنيف. البند التالت (تثبيت الموديل) اتشال — اعتراضه كان في محله.

- [ ] **`Gemini:ApiKey` فاضي = التطبيق ميقومش أصلاً.** دلوقتي لو الـ key ناقص، التطبيق بيقوم عادي وأول request بيروح لـ Gemini ويرجع 4xx — يعني حالة زيادة في التصنيف بتاع الجزء ب. لو وقع عند الـ startup، **الحالة بتختفي من التصنيف خالص**. دوّر على `ValidateDataAnnotations` و `ValidateOnStart` — ونفس الكلام على `Model`.
- [ ] **Timeout صريح على الـ typed client.** الافتراضي مش صفر ومش صغير، وهو اللي **بيولّد** واحدة من حالات الفشل اللي هتصنّفها في الجزء ب — س1 كلها عنه. من غير ما تحدده مش هتقدر تجرّب المسار ده. حط رقم واكتب ليه الرقم ده بالذات لتطبيق موبايل.

### الجزء ب — الـ proxy يفرّق بين أنواع الفشل (ده الشغل الحقيقي)

- [ ] `finishReason` بيتعمله deserialize من `candidates[0]`. القيم اللي Gemini بيرجّعها: `STOP` · `MAX_TOKENS` · `SAFETY` · `RECITATION` · `OTHER`.
- [ ] `TranslateAsync` مبقاش بيرجّع `null` لكل حاجة — بقى بيرجّع نوع بيقول **ايه اللي حصل**، مش بس "فشل".
- [ ] الـ controller بيعمل map لكل حالة لـ status code مختلف. الحالات اللي لازم تتغطى على الأقل:
  - نجاح
  - Gemini رجّع 429 (الـ quota)
  - Gemini رجّع 4xx بسبب الـ key / الـ request بتاعنا
  - Gemini رجّع 5xx أو الشبكة وقعت

- [ ] **جنب كل status code في الكود اكتب سطر تعليق واحد بيقول ليه هو ده.** مش توثيق — دي الطريقة الوحيدة اللي أعرف بيها إنك اخترت مش خمّنت. لو مفيش سبب، يبقى الاختيار غلط.

- `AddHttpClient<T>(client => ...)` — فيه overload بياخد الـ client عشان تظبطه وقت التسجيل بدل الـ constructor

## 🧭 قرار معماري: ازاي الـ service يقول "فشل، والفشل نوعه كذا"

- **اخترنا:** `sealed record` hierarchy — نوع أب واحد تحته `Success` وتحته أنواع الفشل، والـ controller بيعمل عليه `switch` expression.
- **البدائل:**
  1. exceptions مخصصة (`GeminiQuotaExhaustedException`، `GeminiUnavailableException`…) والـ controller يـ catch
  2. record واحد فيه `enum Outcome` + `string? Text` + `string? ModelVersion`
- **ليه الـ hierarchy هنا:**
  - **ده حرفياً الـ `sealed class Failure` بتاعك في الفلاتر.** نفس الفكرة، نفس الـ pattern matching، سينتاكس مختلف. المكسب إن الـ contract بين الجهتين هيبقى مرسوم بنفس الشكل من الطرفين.
  - **بيحافظ على قرار #17.** البديل رقم 2 بيرجّع `string?` تاني — يعني كل متصل لازم يدافع عن نفسه، وده بالظبط اللي اتشال في TASK-003. في الـ hierarchy، `Success` وبس هي اللي فيها `Text`، ومفيهاش `?`. النوع نفسه بيمنع السؤال الغلط.
  - **الفشل هنا مش استثنائي — هو متوقع ويومي.** الـ quota بتخلص كل يوم. الـ exception اللي بتحصل كل يوم مش exception، دي حالة من حالات النظام. الـ exceptions تمنها غالي (stack unwinding) والأهم إنها بتخفي إن ده مسار طبيعي.
- **إمتى كنا هنختار الـ exceptions (البديل 1):** لما يبقى فيه **أكتر من caller** ومحدش فيهم مهتم بالتفصيل، أو لما الفشل يكون لازم يعدّي طبقات كتير من غير ما كل طبقة تشيله في الـ return type. في M4 لما يبقى فيه `IExceptionHandler` مركزي وendpoints كتير، المعادلة دي ممكن تقلب — وساعتها نراجع.
- **الغلطة الشائعة:** إنك تعمل الـ hierarchy وبعدين تحطها في `try/catch` وترمي exception من جوه — فتبقى عامل الاتنين ومكسبتش ولا واحدة. اختار واحدة وامشي عليها لآخر الـ method.

### ❓ "بس إحنا هنعمل Global Error Handler في M4 — ليه الـ hierarchy؟"

> **اعتراض منه 2026-08-20.** سؤال في محله، والـ decision block فوق كان ناقص عشانه — عدّد البدائل من غير ما يحسب إن `IExceptionHandler` جاي بعد تاسكين. الرد:

**الـ global handler مش router — هو أرضية.**

| | `IExceptionHandler` (M4) | الـ hierarchy |
|---|---|---|
| بيتعامل مع | اللي **متوقعتوش** — `DbUpdateException`، null deref، مكتبة وقعت | اللي **متوقعه** ومكتوب في الـ spec |
| شغلته | يمنع stack trace يوصل للعميل + يوحّد شكل `ProblemDetails` | يقرر الرد المقصود لكل حالة |
| بيتكتب | مرة واحدة للـ API كله | لكل حالة business |

- **الـ quota بتخلص كل يوم.** الحاجة اللي بتحصل كل يوم مش exception — دي حالة من حالات النظام. رميها exception = الـ log بيمتلي ERROR + stack traces لحاجة الكود متوقعها ومتصرف فيها صح.
- **الدليل من المشروع نفسه:** في M5 مع الاشتراكات، "الـ quota خلصت" مش هتفضل 503 — هتبقى **429 + كام حرف فاضل + لينك الترقية**. ده رد بيتركّب في الـ endpoint. لو عاش جوه `catch` مركزي، يبقى منطق الاشتراكات جوه handler عام — وهيتشال منه تاني.
- **نقطة عملية:** الـ handler **مش موجود دلوقتي**. `throw` النهاردة = 500 + stack trace للعميل. يعني هيضطر يكتب `catch` في الـ controller برضه — نفس الشغل، بس من غير مساعدة الـ compiler على الحالات الناقصة.
- **إمتى يبقى هو صح:** لما يبقى فيه **أكتر من caller** وطبقات بينهم مش مهتمة بالتفصيل، فيضطر يشيل الـ failure في الـ return type بتاع كل طبقة في الطريق. دلوقتي فيه caller واحد.
- **والقرار ده رخيص في الرجوع** — كل record بيتحول لـ exception class في دقيقتين لو M4 قلبت المعادلة. النقاش الغالي هو الـ status codes، مش ده.

### ⚠️ الفخ في الـ status codes — اقراه قبل ما تختار

هتتغري ترجّع **429** لما الـ Gemini quota تخلص. **متعملش.**

الـ 429 معناها "**انت** يا عميل بعت طلبات كتير". بس العميل اللي أهو مبعتش غير طلب واحد — إحنا اللي الـ key بتاعنا خلص. لو حرقت الـ 429 على الحالة دي، هتعمل ايه في M5 لما يبقى فيه اشتراكات وquota حقيقية لكل مستخدم وتحتاج تقول للعميل "**انت** خلصت رصيدك"؟ مش هيبقى قدامك كود يفرّق.

الـ status codes زي أسماء الحقول في الـ contract — تخصيصها قرار بيتقفل، والرجوع فيه بيكسر تليفونات في السوق.
